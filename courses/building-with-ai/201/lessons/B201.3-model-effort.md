# B201.3 — Choose a Model and Effort Level in Practice

**Duration:** 4 minutes 9 seconds (rendered cut, 2026-09-26)  
**Release:** early October 2026. Model names, effort levels, and defaults change with each release; what effort trades off, and testing it on your own task, are the durable part.  
**Timing basis:** 136 words per minute, section gaps 0.8s (1.0s before Continue Learning)  
**Audience assumption:** The learner has seen F101.6 (model decides how capable, effort decides how hard it works) and can define a checkable task  
**Key concept:** Effort sets how much Claude checks and decides on its own, and so how much you stay in the loop. Spend it where the work hides edge cases, and prove it on your own task.  
**Learner outcome:** Run one recurring task at two effort levels, and write a rule for when to raise effort, backed by what the check showed.

## A-roll script

(0:00–0:10) | Series Introduction

Welcome to the Analytics AI Enablement education series. Today in Building with AI, we choose a model and effort level in practice.

(0:11–0:50) | What Effort Changes

Foundations 101 split the two settings: the model decides how capable Claude is, and effort decides how hard it works. Thariq Shihipar, on Anthropic's Claude Code team, tested every effort level on the same tasks. He found that effort mostly changes two things: how much Claude checks its own work, and how much it decides on its own.

Think of a deadline. Given one hour, you'd build a solid first version and expect feedback. Given twelve, you'd test, second-guess, and polish without asking. Effort tells Claude which deadline it has.

(0:51–1:30) | How Much You Stay in the Loop

So effort also decides how much you stay in the loop. He gave Claude a vague request: build a workout tracker. At low effort, it took about a minute and a half and returned a simple log and chart. At max, it took over an hour, returned much more, and Claude made more of the choices itself. With a detailed spec, the levels came out much closer.

Low effort gives you a quick draft to steer. High effort does more of the work, and makes more assumptions for you.

(1:31–2:19) | Where Effort Pays Off

Effort pays off when the work hides edge cases. One benchmark task was a data analysis: from protein measurements, find which of eight treatments resemble a target tissue. At low effort, Claude picked one reasonable way to prepare the data, ran it, and reported. At high, it tried two ways, saw the answer change, and worked out why before choosing. It went from zero of five attempts correct to four.

That's the reconciliation you'd want before a number reaches a stakeholder. But across the benchmark, more effort cut missed edge cases without fixing a wrong approach. If the plan is wrong, fix the task, or try a stronger model.

(2:20–2:51) | A Loop for Everyday Work

Here's a loop he uses, adapted for analytics. First, ask Claude to interview you about the analysis: the grain, the date window, what counts. Second, draft on low or medium effort. Third, review that it got the gist, and iterate quickly. Fourth, raise effort to high and ask Claude to verify: reconcile totals, test nulls and date boundaries, and try a second method. You can change effort mid-conversation with slash effort.

(2:52–3:51) | Test It on Your Own Task

Treat his rule of thumb as a starting point. Models and their defaults change with each release, so test it on your own work. Pick one recurring task with two or three checks. Run it at the default, and record four things: which checks passed, what it missed, how long it took, and how much it used. Then change only the effort, and run it again. More effort costs more time and tokens, so it has to buy something your checks can see.

If the higher run caught edge cases the first one missed, keep high effort for the verify step. If both runs took the wrong approach, go back to the task or the model. One run is a practical check, not an evaluation. A workflow you rely on needs repeated runs.

(3:52–4:05) | Write Your Rule

Finish with one sentence. Use the default for this. Raise effort when this, because the check showed this. Thariq's full article, with the benchmark details, is linked on the course page.

## Immediate exercise and feedback loop

Pick one recurring task with two or three concrete checks. Run it at the default effort and fill the run card: checks passed, what it missed, time, and usage. Change only the effort and run it again. Finish the rule: "Use the default for ___. Raise effort when ___, because the check showed ___." A reviewer should reject a rule that cites time or preference alone without a check result.

## Boundary

The article's numbers are Anthropic's own benchmark runs (five attempts per task, internal settings), and the build examples are single runs of software tasks. They show a direction, not a guarantee for analytics work. The failure kinds in the edge-case finding were labelled by a model judge and are approximate. The rule of thumb is one engineer's practice; the default effort and the levels a model supports come from the product and from Aledade's setup, which change often. One two-run comparison supports a decision about one task, not a claim about a model or level in general; repeated trials across representative tasks belong to the next level.
