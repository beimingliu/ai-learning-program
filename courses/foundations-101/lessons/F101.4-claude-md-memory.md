## A-roll script

(0:00–0:10.94) | Series Introduction

Welcome to the Analytics AI Enablement education series. Today in Foundations, we focus on CLAUDE.md and auto memory.

(0:10.94–0:35.16) | The File Everyone Mentions

If you have worked in Claude Code for a while, you have seen a file called `CLAUDE.md` mentioned somewhere, and don't quite know what it is or whether you should be updating it.

You may also have watched Claude say it saved a memory, without you asking it to.

Those are the two ways knowledge is saved between sessions. One of them is yours to write. The other you can mostly leave alone.

(0:35.16–1:26.36) | Write Less, Not More

Here is the counterintuitive part.

Every model release is more capable than the last. When Anthropic shipped the new Claude 5 models, the team cut roughly eighty percent of the system prompt, the standing instructions the model receives before you type anything. It is removed because the model itself is smarter and more capable.

Your instinct with `CLAUDE.md` is to write more, and explain with more edge cases and anti-patterns. Resist that.

Today's models do competent work without being told how. Spend the file on what they cannot infer: boundaries and guardrails. What not to touch. What never to run. Where the source of truth lives, and which tool or MCP reaches it.

Leave the specifics out unless the business definition matters, or Claude got it wrong multiple times.

(1:26.36–2:22.96) | Where You Put It

Where you put the file decides who it applies to.

Your **user** file follows you into every project on your machine. This is where personal working style belongs: examples like keep responses concise, never use a pie chart, name variables properly. Keep it under a hundred lines.

A **project** file sits in the folder your team shares, and travels with the project. Shared data locations, metric conventions, and team standards belong there. A well-defined metric stops Claude inventing a plausible but wrong calculation.

A file in a **subdirectory** applies to that folder only, and loads when the agent reads files inside it. A Snowflake-specific rule stays out of the way until the work is actually about Snowflake.

All of them load, and none replaces another. If two of them disagree, Claude may follow either one. So delete the line that is wrong, rather than trying to out-rank it.

(2:22.96–2:46.72) | Leave the Other One Alone

The second mechanism is auto memory. Claude keeps its own notes: your preferences, corrections you gave it, details it could not read from the files. It is on by default, and it stays on your machine.

You write `CLAUDE.md` by hand. Auto memory manages itself.

For most of your work that is the right division. Edit the first. Leave the second alone.

(2:46.72–3:06.80) | Write One Line

Find one boundary you have explained to an AI tool more than once.

Write it as a single specific instruction: “Never write to the source files,” not “be careful with the data.”

Run `/memory`, open the file for the scope that matches who needs it, and paste it in. Then run `/context` to confirm it loaded.

## Immediate exercise and feedback loop

Write one boundary you have explained to an AI tool more than once, as a single specific, checkable line. Save it into the scope that matches who needs it using `/memory`, then confirm with `/context` that it loaded. A reviewer should be able to say whether the line is specific enough to check, and whether it is a boundary rather than an instruction the model no longer needs.

## Boundary

CLAUDE.md and auto memory are persisted guidance loaded into context. They are not access control, policy enforcement, or a guarantee of compliance. A managed file deployed by your organization cannot be turned off, but it is still guidance. Ordering does not resolve a contradiction between two files; only editing them does. Enforcement lives in permissions and policy, covered in Building with AI 201.
